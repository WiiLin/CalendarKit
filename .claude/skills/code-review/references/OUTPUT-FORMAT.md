# 審查報告輸出格式

本文件定義程式碼審查的標準輸出格式。所有審查報告應遵循此格式。

## 格式概述

審查結果應以清晰、結構化的繁體中文呈現，包含以下區塊：

1. 📋 審查摘要
2. 🔍 技術觀察
3. ⚠️ 識別的問題（🔴 Blocker / 🟡 Should fix / 🟢 Nit）
4. ✅ 符合最佳實踐的部分（選擇性，僅列出關鍵技術標準符合項目）
5. 📊 總體評分
6. 💡 後續建議

**重要原則：**
- **避免重複內容**：每個技術觀察只在最相關的區塊出現一次
- **記憶體/執行緒安全**：在「技術觀察」區塊統一描述，不在後續區塊重複
- **客觀陳述**：禁止讚美（「做得好」、「優秀」），只客觀列出符合標準的事實

---

## 📋 審查摘要

根據審查類型，使用對應的摘要格式：

### 針對未 commit 的變更

```markdown
## 📋 審查摘要

- **審查範圍**：未 commit 的變更
- **修改的檔案數量**：X 個
- **新增行數**：+XXX
- **刪除行數**：-XXX
- **審查時間**：YYYY-MM-DD
```

### 針對特定 commit / 分支

```markdown
## 📋 審查摘要

- **Commit / 分支**：`abc123` 或 `feat/#26133`（基底 `develop`）
- **訊息 / 對應票**：XXX（Redmine #26133）
- **修改的檔案數量**：X 個
- **審查時間**：YYYY-MM-DD
```

### 針對指定檔案

```markdown
## 📋 審查摘要

- **檔案**：[檔案路徑](檔案路徑)
- **檔案大小**：XXX 行
- **審查時間**：YYYY-MM-DD
```

---

## 🔍 技術觀察（Technical Observations）

**目的：** 高層次描述架構決策和風險評估，避免在後續區塊重複。

### 當前架構決策

列出程式碼中採用的架構決策和模式：

```markdown
## 🔍 技術觀察

### 當前架構決策

- **邏輯歸屬**：列印分流邏輯放在 EZPrinterKit，兩個 App 共用
- **錯誤處理**：紙寬未設定丟 `paperWidthNotConfigured`，不塞預設值
- **記憶體管理**：閉包使用 `[weak self]`，無 retain cycle 風險
```

**要點：**
- 識別當前採用的模式（不要讚美或批評）
- 說明這些模式的權衡
- **記憶體/執行緒安全在此統一描述**，不在「符合最佳實踐」區塊重複細節

### 潛在風險評估

識別當前實作可能在以下情況失敗：

```markdown
### 潛在風險評估

#### 邊界條件
- 當陣列為空時，`first!` 會導致 crash
- 並發訪問 `cache` 字典可能導致資料競爭

#### 資源限制
- 網路請求沒有 timeout，可能無限等待
- 印表機離線時佇列堆積無上限

#### 生命週期事件
- token 過期後 retry 路徑未覆蓋 framework 自己的 Session
```

**要點：**
- 專注於「在什麼情況下會失敗」，提供具體的場景，解釋風險的影響

## ⚠️ 識別的問題（Issues Identified）

依照影響程度分三級（與團隊 review 慣例一致）：

### 🔴 Blocker（必須修正，修復後再審）

錯誤邏輯、資料遺失、crash、安全問題——對系統穩定性或使用者有重大影響。

**格式：**
```markdown
### 🔴 Blocker

#### 1. 強制解包導致潛在 Crash

**位置**：[LoginViewModel.swift:45](ezDesigner/ezDesigner/Swift/LoginViewModel.swift#L45)

**風險**：
當 `users` 陣列為空時，`users.first!` 會導致 runtime crash。這會在沒有註冊使用者時發生。

**影響**：
- App crash，使用者無法使用

**同型出現點**：
- ezstore-ios 的同名流程無此問題（已確認）/ [同檔:82](路徑#L82) 亦同

**解決方案**：
使用 optional binding 或 optional chaining 安全存取。
```

**要點：**
- 清楚說明風險和影響，提供具體可行的解決方案，包含檔案位置連結
- **列出同型出現點掃描結果**（含另一個 App / framework call site）

### 🟡 Should fix（強烈建議修正，不觸發新一輪審查）

影響可維護性、效能或未來擴展性的問題（技術債務）。

**格式：**
```markdown
### 🟡 Should fix

#### 1. ViewController 職責過重

**位置**：[HomeViewController.swift](路徑)

**問題**：
VC 包含 500+ 行程式碼，同時處理網路請求、資料轉換、版面組裝。違反單一職責原則與 ui-view-structure 規範。

**權衡**：
- **當前做法**：所有邏輯集中在一處，容易找到
- **成本**：難以測試、難以理解、高風險的修改

**替代方案**：
1. 版面區塊抽成 `UIView` 子類
2. 資料轉換移到 model / helper
```

### 🟢 Nit（選擇性修正）

風格、命名、慣例層級的次要問題。

**格式：**
```markdown
### 🟢 Nit

1. [NetworkService.swift:120](路徑#L120) - 通知名稱用散落字串，建議集中定義
2. [檔案:行號](路徑) - 變數命名可以更清晰（`data` → `profileData`）
```

**要點：**
- 一行一條即可，不要過度展開（這是次要問題）

### 範圍外建議（不擋此次變更）

與本次變更**不同根因**的既有問題，一句話 + 定位點：

```markdown
### 範圍外建議（不擋此次變更）

- [EZHairAPIManager.m:2603](路徑#L2603) - 既有 dead code，建議另開票清理
```

## ✅ 符合最佳實踐的部分（Standards Compliance）

**使用時機：** 僅在有關鍵技術標準符合項目時才加入此區塊。不是必要區塊。

**目的：** 客觀列出符合技術標準的實作，非讚美，而是確認風險已被妥善處理。

**格式：**
```markdown
## ✅ 符合最佳實踐的部分

### 記憶體與執行緒安全
- 所有非同步閉包使用 `[weak self]` 避免 retain cycle（[檔案:42](路徑#L42)）
- UI 更新統一回主執行緒

### 錯誤處理
- 紙寬未設定明確丟錯誤導設定頁，未塞預設值（[檔案:49](路徑#L49)）
```

**要點：**
- **僅列出關鍵標準**：記憶體安全、執行緒安全、錯誤處理、測試覆蓋
- **附帶檔案位置**：每個陳述都應有具體檔案行號
- **禁止主觀判斷**：「設計良好」、「優秀實作」等詞彙禁用，改用「符合 X 標準」
- **簡潔為主**：不超過 10 條項目，每條 1-2 行；沒有值得列的就省略此區塊

## 📊 總體評分

使用星級評分（1-5 星）評估各個維度：

```markdown
## 📊 總體評分

- **程式碼品質**：★★★★☆
- **可維護性**：★★★★★
- **可測試性**：★★★☆☆
- **效能**：★★★★☆
- **架構設計**：★★★★☆
```

**評分標準（嚴格模式）：**
- ★☆☆☆☆：嚴重問題，需要大幅重構
- ★★☆☆☆：多個重要問題，需要顯著改進
- ★★★☆☆：有改進空間，存在技術債務（**預設標準**）
- ★★★★☆：符合標準，有少數次要改進點
- ★★★★★：接近完美，無明顯缺陷（**極為罕見，需明確說明理由**）

**嚴格評分原則：**
- **預設懷疑**：大多數程式碼應落在 ★★★☆☆ 範圍（有技術債務是常態）
- **禁止全五星**：不可能所有維度都達到 ★★★★★
- **不要讚美**：評分是客觀測量，非價值判斷

**評分示例：**
- 有 1 個強制解包風險 → 程式碼品質 ★★★☆☆
- 有記憶體洩漏可能 → 程式碼品質 ★★☆☆☆
- App 端長出應屬 framework 的邏輯 → 架構設計 ★★★☆☆

## 💡 後續建議

列出整體改進方向和重構建議：

```markdown
## 💡 後續建議

### 短期改進（本次或下一次變更）

1. **修正 Blocker**：處理強制解包的 crash 風險
2. **添加錯誤處理**：為網路請求添加 timeout

### 中長期優化

1. **重構巨型 VC**：版面區塊抽 view 子類
2. **共用邏輯上移**：把兩個 App 重複的列印邏輯移進 EZPrinterKit

### 技術債務追蹤

建議為以下項目建立 Redmine 票：
- [ ] #XXXXX：重構 HomeViewController
- [ ] #XXXXX：清理 EZHairAPIManager dead code
```

**要點：**
- 區分短期和長期建議，提供具體可行的步驟，建議建立追蹤票

## 特殊情況處理

### 沒有明顯問題的情況

如果審查後沒有發現 Blocker，使用簡化格式：

```markdown
## 📋 審查摘要
[...]

## 🔍 技術觀察

### 當前架構決策
- **記憶體管理**：閉包正確使用 `[weak self]`

### 潛在風險評估
未發現明顯的 crash 風險或記憶體洩漏問題。

## 📊 總體評分

- **程式碼品質**：★★★★☆
- **可維護性**：★★★★☆

## 💡 後續建議

### 短期改進
1. （若有 Nit 列於此）
```

**注意：** 即使沒有明顯問題，也應指出改進空間，評分不應全部四星以上。

### 只有次要問題的情況

如果只有 🟢 Nit，可以簡化「識別的問題」區塊為條列，一行一條。

## 檔案引用格式

在報告中引用檔案和程式碼時，使用以下格式：

- **檔案引用**：`[檔案名稱.swift](相對路徑/檔案名稱.swift)`
- **行號引用**：`[檔案名稱.swift:42](相對路徑/檔案名稱.swift#L42)`
- **範圍引用**：`[檔案名稱.swift:42-51](相對路徑/檔案名稱.swift#L42-L51)`

這樣使用者可以直接點擊連結跳轉到對應的程式碼位置。

## 審查原則提醒

在輸出審查報告前，確認：

- ✅ 只發布真正有價值的評論
- ✅ 解釋「為什麼」，不只是「是什麼」
- ✅ 提供具體可行的建議
- ✅ 尊重專案的編碼慣例
- ✅ 區分 🔴 Blocker 與 🟡/🟢 次要建議；只有 Blocker 觸發「修復後再審」
- ✅ 所有評論使用繁體中文
- ✅ 避免讚美或價值判斷
- ✅ 專注於風險和權衡
